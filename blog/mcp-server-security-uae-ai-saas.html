MCP server security is becoming a real production concern for UAE companies building AI agents, internal copilots and automated SaaS workflows. Model Context Protocol makes it easier for an AI system to discover tools and call business APIs, but it also gives the model a path to customer data and operational actions. This guide explains the controls I would require before connecting an MCP server to a live product.

The official MCP 2026-07-28 release moved the core protocol to stateless requests and updated authorization. The NSA MCP guidance also warns about dynamic tool calls, implicit trust and shared context. As UAE organisations move services towards AI-led operations, these controls need to exist before agents receive real permissions.

MCP server security starts with a strict trust boundary

An MCP server should be treated as a privileged API, not a harmless chatbot plugin. The model can be manipulated by untrusted documents, web pages or user input. Your server must decide what is allowed even when the model asks confidently.

I would separate read tools from write tools, avoid generic database or shell access, and publish narrow actions such as get_invoice_status or create_support_draft. Tool schemas and dependencies should be versioned and reviewed like normal production code.

Use OAuth and least privilege for every MCP request

A remote MCP server needs authenticated callers, short-lived tokens and scopes tied to the exact resource. The official MCP TypeScript SDK authorization guide shows bearer-token enforcement, audience validation and per-operation scope checks. Validating only a token signature is not enough; a token issued for another API must not work against your MCP endpoint.

const auth = requireBearerAuth({
  verifier: verifyAccessToken,
  requiredScopes: ['mcp:read'],
  expectedResource: new URL('https://api.example.ae/mcp')
});
app.all('/mcp', auth, handler);

In a multi-tenant SaaS product, the verified identity must flow into every tool handler. Never accept a tenant ID from the model and trust it directly. Resolve the tenant from the authenticated user, then apply the same row-level and role-based rules used by the normal application.

Add human approval before high-impact AI actions

Reading a knowledge article is not equal to issuing a refund, updating payroll or deleting a record. High-impact tools need a confirmation screen showing the exact action, target and important parameters. Approval should expire and must be checked by the server, not represented by a sentence in the prompt.

The new MCP specification supports multi round-trip requests for missing input and confirmation. That improves the flow, but it does not replace business authorization. A finance user may approve an invoice action; a support user should not gain that permission because the agent selected the same tool.

Protect data, secrets and UAE customer context

Send the minimum context required for each call. Keep API keys in a server-side secret store, redact sensitive fields from model-visible responses and block unrestricted outbound requests. Tool output is untrusted input too, so validate it before another privileged tool can act on it.

For UAE products handling personal data, map which provider receives the prompt, where logs are stored, how long traces remain and whether data crosses borders. My UAE PDPL SaaS checklist covers the wider privacy questions.

Log decisions and test abuse cases

Production logs should capture the caller, tenant, tool, policy decision, outcome and trace ID without dumping secrets or private prompts. Set rate limits per tenant and tool. Alert on repeated denials, unusual write volume, changed tool catalogs and calls outside normal workflows.

Testing must include prompt injection, cross-tenant IDs, expired tokens, missing scopes, malicious URLs, retries and partial failures. I also test what happens when the model chooses the wrong tool. The safe result is a denied or reversible action, not a clever prompt that usually works.

MCP security checklist before production

  • Inventory every server, tool, owner and deployed version.
  • Require OAuth, audience checks and short-lived credentials.
  • Apply tenant isolation and role checks inside each handler.
  • Remove shell, raw SQL and broad file access.
  • Require server-verified approval for sensitive writes.
  • Validate inputs, outputs, destinations and updates.
  • Record audit evidence without unnecessary secrets.
  • Run adversarial tests and define a fast kill switch.

Practical takeaway

A secure MCP server is still a carefully designed backend service. The protocol can simplify AI integration, but OAuth, tenant isolation, approvals, observability and failure handling remain your responsibility. For UAE AI SaaS, I would launch with a small read-only tool set, measure real usage, then add tightly scoped actions one at a time.
